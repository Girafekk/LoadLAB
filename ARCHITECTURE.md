# ARCHITECTURE — архитектура LoadLab

## 1. Общая схема

LoadLab состоит из трёх независимых частей. Они общаются только через чётко
определённые границы: браузер ↔ backend по HTTP, backend ↔ база данных по SQL.

```
┌──────────────────┐   HTTP (JSON)    ┌──────────────────┐     SQL      ┌──────────────────┐
│     Frontend     │ ───────────────► │     Backend      │ ───────────► │    PostgreSQL    │
│  Next.js / React │ ◄─────────────── │     FastAPI      │ ◄─────────── │   (в Docker)     │
│  localhost:3000  │    /api/v1/...   │  localhost:8001  │              │  localhost:5432  │
└──────────────────┘                  └──────────────────┘              └──────────────────┘
   то, что видит                         правила и логика                  хранение данных
   пользователь                          платформы
```

| Часть | Зона ответственности | Чего не делает |
|---|---|---|
| Frontend | Отображение страниц, действия пользователя | Не обращается к базе данных, не хранит секреты |
| Backend | Логика, проверка данных, доступ к базе | Не формирует HTML-страницы |
| PostgreSQL | Надёжное хранение данных | Не содержит бизнес-логики |

Frontend и backend можно разрабатывать, запускать и обновлять отдельно друг от друга.
Единственный «договор» между ними — API, описанное в OpenAPI.

## 2. Frontend

Next.js (App Router), React, TypeScript, Tailwind CSS, shadcn/ui.

```
frontend/src/
├── app/                  # Страницы. Папка = адрес на сайте
│   ├── layout.tsx        # Общий каркас: шрифты, шапка, футер, тема
│   ├── page.tsx          # Главная страница  →  /
│   ├── learn/page.tsx    # Программа курса   →  /learn
│   ├── learn/lessons/[lessonId]/page.tsx  # Урок  →  /learn/lessons/{id}
│   ├── profile/page.tsx  # Профиль           →  /profile
│   ├── profile/tools/page.tsx  # Мои материалы →  /profile/tools
│   ├── trainers/page.tsx  # Тренажёры        →  /trainers
│   ├── admin/page.tsx    # Админка: курс      →  /admin
│   ├── admin/lessons/[lessonId]/page.tsx  # Редактор урока → /admin/lessons/{id}
│   ├── admin/students/page.tsx  # Прогресс учеников → /admin/students
│   ├── login/page.tsx    # Вход              →  /login
│   ├── register/page.tsx # Регистрация       →  /register
│   └── globals.css       # Цвета и тема (светлая и тёмная)
├── components/
│   ├── ui/               # Базовые элементы shadcn/ui: кнопка, карточка, поле ввода
│   ├── layout/           # Шапка, футер, логотип, переключатель темы, меню
│   ├── auth/             # Формы входа и регистрации, профиль, AuthProvider
│   ├── learn/            # Прогресс ученика, страница урока, квиз и материалы урока
│   ├── tools/            # Страница «Мои материалы»
│   ├── trainers/         # HTTP, SQL, Linux и анализ
│   ├── admin/            # Панель администратора: курс, урок, ученики
│   └── home/             # Разделы главной страницы
├── content/              # Тексты и данные для страниц (программа курса, тексты форм)
└── lib/                  # Вспомогательный код: вызовы API, проверки форм, тема
```

Принципы:

- **Страница собирается из компонентов.** Файл страницы только перечисляет разделы.
- **Цвета — только через токены** (`bg-background`, `text-brand`), заданные в `globals.css`.
  Так обе темы поддерживаются автоматически.
- **Все обращения к backend — через `lib/api.ts`.** Адрес API задаётся переменной
  `NEXT_PUBLIC_API_URL`.
- **Серверные компоненты по умолчанию.** `"use client"` — только там, где нужна
  интерактивность (переключатель темы, меню, формы, индикатор сервера).
- **Кто вошёл — знает `AuthProvider`.** Он один раз спрашивает backend (`GET /auth/me`)
  и раздаёт ответ шапке и страницам. Токен сессии в JavaScript не хранится и не читается.
- **Проверки в браузере — для удобства, а не для защиты.** Редирект гостя с `/profile`
  и проверка полей формы лишь экономят время человека; права проверяет backend.
- Тема хранится в классе `dark` на `<html>` и в `localStorage`; небольшой скрипт
  выставляет её до отрисовки, чтобы страница не «мигала».

### Слои и направление зависимостей

```
api/endpoints  →  services  →  models / db
      │                            ▲
      └────────  schemas  ─────────┘ (схемы описывают данные на границе API)
```

- **endpoints** принимают запрос, вызывают сервис, возвращают ответ. Логики в них нет.
- **services** содержат правила платформы и не знают про HTTP.
- **models** и **db** отвечают только за хранение.
- Зависимости направлены строго вниз: сервис не импортирует endpoint.

### Как добавить новую область (например, курсы)

1. `models/course.py` — таблица; импортировать её в `models/__init__.py`.
2. Миграция Alembic.
3. `schemas/course.py` — формы запросов и ответов.
4. `services/course_service.py` — логика.
5. `api/endpoints/courses.py` — маршруты; одна строка подключения в `api/router.py`.
6. Тесты в `tests/`.

Существующие файлы при этом не переписываются. Так будут добавлены авторизация,
пользователи, курсы, уроки, квизы, AI-сервисы и административное API.

### Соглашения API

- Все адреса начинаются с `/api/v1`. Несовместимые изменения — только в новой версии (`/api/v2`).
- Документация: `/api/v1/docs` (Swagger UI), `/api/v1/redoc`, `/api/v1/openapi.json`.
- Любая ошибка имеет один формат:

  ```json
  {"error": {"code": "not_found", "message": "Not Found", "details": null}}
  ```

- Подробности внутренних ошибок пишутся в лог и не отдаются клиенту.

### Авторизация

Вход устроен на серверных сессиях. Браузер хранит только случайный токен в cookie,
а всё остальное — на сервере.

```
Браузер                         Backend                          PostgreSQL
   │  POST /auth/login             │                                  │
   │  email + пароль ─────────────►│  сверяет пароль с хэшем Argon2 ─►│ users
   │                               │  создаёт токен, хранит SHA-256 ─►│ sessions
   │◄── Set-Cookie: loadlab_session=токен (HttpOnly, SameSite=Lax)    │
   │                               │                                  │
   │  GET /users/me                │                                  │
   │  Cookie: токен ──────────────►│  SHA-256(токен) → сессия → user ►│ sessions ⨝ users
   │◄── профиль                    │                                  │
```

Цепочка проверки каждого запроса: **cookie → `sessions` → `users`**.

- **Пароль** хранится только как хэш Argon2 (`core/security.py`), нигде не логируется
  и не возвращается в ответах.
- **Токен сессии** — `secrets.token_urlsafe(32)`. В базе лежит только его SHA-256,
  поэтому по украденной базе войти в чужую учётную запись нельзя.
- **Cookie** `loadlab_session`: `HttpOnly` (недоступна JavaScript), `SameSite=Lax`,
  `Path=/`, срок 7 дней; `Secure` — только в production. Имя задаётся настройкой
  `SESSION_COOKIE_NAME`: стенд production-репетиции использует своё имя, потому что
  cookie не разделяются по портам и два стенда на `localhost` иначе затирали бы
  сессии друг друга.
- **Срок сессии** — 7 дней. Просроченные сессии удаляются при каждом успешном входе
  через `POST /auth/login`. Выход удаляет сессию из базы: старый токен перестаёт работать сразу.
- **Email** приводится к единому виду (без пробелов по краям, нижний регистр).
- **Роли** (`student`, `admin`) хранятся в `users.role` и проверяются только на сервере
  зависимостями из `api/deps.py`: `get_current_user` (нужен вход, иначе 401)
  и `require_admin` (нужна роль администратора, иначе 403).
- **CSRF.** Для POST, PUT, PATCH и DELETE проверяется заголовок `Origin`
  (`core/csrf.py`): он должен совпадать с адресом frontend из `CORS_ORIGINS`
  или с адресом самого API (для страницы документации). Иначе — 403.
- **Перебор паролей.** Не более 5 попыток входа за 15 минут на пару «IP-адрес + email»,
  далее 429 (`core/rate_limit.py`). Попытка занимается одной атомарной операцией
  до проверки пароля: параллельные запросы не проскакивают лимит, пока первый ещё
  сверяет хэш Argon2. Счётчик хранится в памяти процесса: при нескольких
  процессах backend или после перезапуска он не общий — тогда потребуется Redis.

| Маршрут | Что делает | Ошибки |
|---|---|---|
| `POST /auth/register` | Создаёт ученика и сразу выполняет вход | 409 — email занят, 422 — некорректные данные |
| `POST /auth/login` | Вход, ставит cookie | 401 — неверные данные, 403 — запись отключена, 422 — некорректные данные, 429 — перебор |
| `POST /auth/logout` | Удаляет сессию и cookie | — |
| `GET /auth/me` | Кто вошёл: `id`, `email`, `role` | 401 |
| `GET /users/me` | Профиль | 401 |
| `GET /admin/ping` | Проверка прав администратора | 401, 403 |

Администратор создаётся командой `python -m app.cli create_admin`; через API получить
роль администратора нельзя.

### Курсы, уроки и прогресс

Учебный каталог читается из базы, а не из файлов: `courses` → `modules` → `lessons`
→ `lesson_blocks`. Правила доступа:

- **Программа курса видна всем.** Гость получает модули и опубликованные уроки,
  но без личного прогресса (`progress: null`); вошедший ученик — со счётчиками.
- **Урок доступен только после входа** (иначе 401). Черновой урок и урок
  неопубликованного курса выглядят как отсутствующие (404) — так черновики
  не утекают даже по прямому адресу.
- **Прогресс принадлежит только своему ученику.** `user_id` берётся из сессии
  и никогда из тела запроса или адреса — поэтому чужой прогресс не изменить (IDOR).
- **Отметка идемпотентна:** повторный `POST` возвращает 204 и не создаёт дубль,
  `DELETE` снимает отметку. Оба запроса проходят обычную проверку Origin (CSRF).

| Маршрут | Что делает | Ошибки |
|---|---|---|
| `GET /courses/current` | Курс, модули, опубликованные уроки и прогресс | 404 — курс не опубликован |
| `GET /lessons/{id}` | Урок с блоками по порядку | 401 — гость, 404 — нет или черновик |
| `POST /lessons/{id}/complete` | Отметить урок пройденным | 401, 403 — CSRF, 404 — нет или черновик |
| `DELETE /lessons/{id}/complete` | Снять отметку | 401, 403, 404 |

`GET /courses/current` отвечает фиксированным числом запросов к базе: курс с
модулями и уроками загружается заранее (`selectinload`), пройденные уроки —
одним запросом. Проценты округляются до целого.

### Квизы

Квиз привязан к уроку или к модулю (ровно один родитель). Сервер проверяет ответы
сам и **не отдаёт признак правильности варианта до отправки**: иначе ответ можно
было бы узнать из ответа API.

- Вопрос бывает с одним или несколькими верными вариантами; интерфейс получает
  подсказку `multiple`.
- После отправки сервер возвращает баллы, проценты и разбор каждого вопроса
  с объяснением. Попытка, ответы и выбранные варианты сохраняются.
- Попыток может быть сколько угодно; история и лучший результат видны ученику.
- Чужие попытки недоступны: `user_id` берётся только из сессии.
- Отправить можно лишь полный набор ответов: пропуск вопроса, вариант из другого
  вопроса или повтор вопроса дают 422.

| Маршрут | Что делает | Ошибки |
|---|---|---|
| `GET /lessons/{id}/quiz` | Квиз урока, вопросы и история попыток | 401, 404 — квиз не опубликован |
| `GET /lessons/{id}/quiz/attempts` | История попыток | 401, 404 |
| `POST /lessons/{id}/quiz/attempts` | Проверить ответы и сохранить попытку | 401, 403 — CSRF, 404, 422 — неполные или чужие ответы |

### Инструменты ученика

Все маршруты требуют входа и работают только со своим учеником: `user_id`
берётся из сессии, чужие записи выглядят как отсутствующие (404).

| Маршрут | Что делает | Ошибки |
|---|---|---|
| `GET`, `PUT /lessons/{id}/note` | Прочитать и сохранить конспект урока | 401, 404 — урок не опубликован |
| `GET`, `POST /lessons/{id}/highlights` | Выделения урока, добавить фразу | 401, 404 |
| `DELETE /highlights/{id}` | Удалить своё выделение | 401, 404 |
| `GET`, `POST /saved-questions`, `PATCH`, `DELETE /saved-questions/{id}` | Сложные вопросы | 401, 404, 422 |
| `GET`, `POST /review-items`, `PATCH`, `DELETE /review-items/{id}` | Список повторения | 401, 404, 422 |
| `GET`, `POST /cheatsheets`, `PATCH`, `DELETE /cheatsheets/{id}` | Шпаргалки | 401, 404, 422 |
| `GET /users/me/weak-topics` | Темы с лучшим результатом ниже 80 % | 401 |

### Тренажёры и AI Teacher

| Маршрут | Что делает | Ошибки |
|---|---|---|
| `GET /trainers/http`, `POST /trainers/http/check` | Упражнения HTTP и проверка метода/пути | 401 |
| `GET /trainers/sql`, `POST /trainers/sql/run` | SQL-упражнения; только безопасный SELECT | 401, 422 |
| `GET /trainers/linux`, `POST /trainers/linux/run` | Виртуальные команды Linux | 401 |
| `GET /trainers/analysis`, `POST /trainers/analysis/check` | Разбор RPS, p95 и насыщения | 401 |
| `POST /ai/teacher/ask` | Вопрос по опубликованному уроку | 401, 404, 422 |
| `GET /ai/teacher/history` | История вопросов ученика | 401 |
| `GET /ai/teacher/recommendations` | Слабые темы для повторения | 401 |
| `GET /ai/teacher/cheatsheet` | Предложение шпаргалки | 401 |

AI Teacher по умолчанию отвечает локально по материалу урока. Если задан
`DEEPSEEK_API_KEY`, используется DeepSeek (`deepseek-chat` по умолчанию).
Резервный вариант — универсальный OpenAI-совместимый провайдер через
`AI_TEACHER_*`. При ошибке внешнего вызова ответ строится локально. Провайдер
и модель видны в `GET /ai/teacher/status` (без секретов). Вопросы и ответы
хранятся в `ai_teacher_messages`, чужая история недоступна.

### Материалы собеседований и пробное собеседование

Администратор загружает TXT, PDF, DOCX или изображение PNG/JPG. Файл сохраняется
в `INTERVIEW_UPLOAD_DIR` (по умолчанию `uploads/interview`), текст извлекается
`pypdf`/`python-docx`, для изображений — Tesseract OCR (русский и английский).
DeepSeek разбирает текст на вопросы; если провайдер недоступен, работает
эвристический разбор по строкам. Вопросы дедуплицируются по fingerprint,
получают тему, сложность, уровень и привязку к уроку.

| Маршрут | Что делает | Ошибки |
|---|---|---|
| `POST /admin/interview/sources` | Загрузить и извлечь материал | 401, 403, 422 |
| `GET /admin/interview/sources` | Список источников | 401, 403 |
| `POST /admin/interview/sources/{id}/analyze` | Разобрать источник | 401, 403, 404, 422 |
| `GET /admin/interview/questions` | Вопросы с фильтром по статусу/теме | 401, 403 |
| `PATCH /admin/interview/questions/{id}` | Тема, сложность, урок, статус | 401, 403, 404 |
| `GET /admin/interview/report` | Покрытие и пробелы | 401, 403 |
| `POST /admin/interview/approve-all` | Подтвердить предложенные вопросы | 401, 403 |
| `POST /admin/interview/reclassify` | Нормализовать темы и привязки | 401, 403 |
| `POST /mock-interviews` | Начать собеседование (5 вопросов) | 401, 422 |
| `POST /mock-interviews/{id}/answers` | Ответ и AI-разбор | 401, 404, 422, 429 |
| `GET /mock-interviews/{id}` | Итоговый отчёт | 401, 404 |

AI-разбор собеседования использует тот же провайдер и общий лимит параллельных
вызовов. Ответы и баллы хранятся в `mock_interview_answers`; чужое
собеседование недоступно. Частота ответов ограничена 15 в минуту.

### Административная панель

Все маршруты `/admin/...` требуют роль администратора. Ученику — 403, гостю — 401.
Редактор работает с теми же таблицами, что и публичная часть, поэтому изменения
сразу видны ученикам после публикации.

| Маршрут | Что делает |
|---|---|
| `GET`, `POST /admin/courses` | Список и создание курсов |
| `GET`, `PATCH`, `DELETE /admin/courses/{id}` | Дерево курса, изменение, удаление |
| `POST /admin/courses/{id}/modules` | Создать модуль |
| `PATCH`, `DELETE /admin/modules/{id}` | Изменить или удалить модуль |
| `POST /admin/modules/{id}/lessons` | Создать урок |
| `GET`, `PATCH`, `DELETE /admin/lessons/{id}` | Урок, изменение, удаление |
| `PUT /admin/lessons/{id}/blocks` | Полностью заменить блоки урока |
| `GET`, `PUT`, `DELETE /admin/lessons/{id}/quiz` | Квиз урока для редактора |
| `GET /admin/students` | Прогресс всех учеников |
| `GET /admin/students/{id}` | Прогресс ученика по модулям |
| `/admin/interview` | Загрузка и разбор материалов собеседований |

Замена квиза удаляет прежние попытки: они ссылаются на старые вопросы и варианты.
Интерфейс предупреждает об этом до сохранения. Версионирование квизов и сохранение
истории при редактировании — задача этапа 9/12 вместе с контентом.

Слабые темы не хранятся отдельной таблицей: они считаются по лучшим попыткам
квизов. Успешная пересдача убирает тему из списка. Записи, привязанные к уроку,
ссылаются на него мягко (`SET NULL`), поэтому удаление урока не стирает личные
материалы ученика; конспект и выделения принадлежат уроку и удаляются вместе с ним.

### Настройки
Читаются классом `Settings` (`core/config.py`) из переменных окружения или файла `.env`
в корне проекта. У пароля базы данных нет значения по умолчанию — без `.env` backend
не запустится и сообщит, чего не хватает.

## 4. База данных

- PostgreSQL 17 в контейнере Docker; данные лежат в именованном томе `loadlab_postgres_data`
  и переживают перезапуск и удаление контейнера.
- Порт открыт только для этого компьютера (`127.0.0.1`).
- Backend работает с базой через SQLAlchemy 2 (драйвер psycopg 3).
- Структура базы меняется **только миграциями Alembic** — не вручную.
- Тесты работают в собственной базе `loadlab_test_<суффикс>`: имя уникально для каждого
  запуска, база создаётся перед тестами и удаляется после. Параллельные прогоны
  не мешают друг другу, база разработки не затрагивается.

### Таблицы и связи

Учебная программа хранится «матрёшкой»: курс состоит из модулей, модуль — из уроков,
урок — из блоков. Отдельно — пользователи и их сессии входа.

```
┌─────────┐ 1    N ┌─────────┐ 1    N ┌─────────┐ 1    N ┌───────────────┐
│ courses │───────►│ modules │───────►│ lessons │───────►│ lesson_blocks │
└─────────┘        └─────────┘        └─────────┘        └───────────────┘
            course_id          module_id          lesson_id

┌─────────┐ 1    N ┌──────────┐
│  users  │───────►│ sessions │
└─────────┘        └──────────┘
             user_id
```

Стрелка «1 → N» — связь «один ко многим»: в дочерней таблице есть столбец с `id` родителя
(внешний ключ). У всех связей задано `ON DELETE CASCADE`: при удалении курса база сама
удаляет его модули, уроки и блоки, а при удалении пользователя — его сессии.

| Таблица | Что хранит | Основные столбцы | Ограничения |
|---|---|---|---|
| `users` | Учётные записи | `email`, `password_hash`, `role`, `is_active` | `email` уникален; `role` — только `student` или `admin` |
| `sessions` | Сессии входа | `user_id`, `token_hash`, `expires_at`, `created_at` | `token_hash` уникален; столбца `updated_at` нет; индексы по `user_id` и `expires_at` |
| `courses` | Курсы | `slug`, `title`, `description`, `is_published` | `slug` уникален |
| `modules` | Модули курса (недели) | `course_id`, `title`, `summary`, `position` | пара (`course_id`, `position`) уникальна |
| `lessons` | Уроки | `module_id`, `title`, `summary`, `estimated_minutes`, `position`, `is_published`, `content_key` | пара (`module_id`, `position`) уникальна; (`module_id`, `content_key`) уникальна; ключ не меняется при переименовании |
| `lesson_blocks` | Части урока | `lesson_id`, `type`, `content` (JSONB), `position` | пара (`lesson_id`, `position`) уникальна; `type` — один из 7 типов |
| `lesson_progress` | Отметки «урок пройден» | `user_id`, `lesson_id`, `completed_at` | составной первичный ключ (`user_id`, `lesson_id`); индекс по `lesson_id` |
| `quizzes` | Квизы уроков и модулей | `lesson_id` или `module_id`, `title`, `description`, `is_published` | ровно один родитель; `lesson_id` уникален |
| `quiz_questions` | Вопросы квиза | `quiz_id`, `kind`, `text`, `explanation`, `position` | пара (`quiz_id`, `position`) уникальна; `kind` — один из 5 типов |
| `quiz_options` | Варианты ответа | `question_id`, `text`, `is_correct`, `position` | пара (`question_id`, `position`) уникальна |
| `quiz_attempts` | Попытки прохождения | `quiz_id`, `user_id`, `score`, `max_score`, `created_at` | индексы по квизу и ученику |
| `quiz_attempt_answers` | Ответ на вопрос в попытке | `attempt_id`, `question_id`, `is_correct` | пара (`attempt_id`, `question_id`) уникальна |
| `quiz_attempt_selected_options` | Выбранные варианты | `answer_id`, `option_id` | составной первичный ключ; ссылочная целостность на уровне базы |
| `lesson_notes` | Конспект ученика по уроку | `user_id`, `lesson_id`, `content` | пара (`user_id`, `lesson_id`) уникальна |
| `lesson_highlights` | Выделенные определения | `user_id`, `lesson_id`, `text` | индекс (`user_id`, `lesson_id`) |
| `saved_questions` | Сложные вопросы ученика | `user_id`, `lesson_id`, `text`, `is_resolved` | урок необязателен; при удалении урока — `SET NULL` |
| `review_items` | Список повторения | `user_id`, `lesson_id`, `title`, `note`, `is_done` | урок необязателен |
| `cheatsheets` | Личные шпаргалки | `user_id`, `lesson_id`, `title`, `content` | урок необязателен |
| `ai_teacher_messages` | История вопросов AI Teacher | `user_id`, `lesson_id`, `question`, `answer`, `mode` | индексы по `user_id` и `lesson_id`; каскад с пользователем и уроком |
| `interview_sources` | Загруженные материалы собеседований | `uploaded_by`, `filename`, `stored_name`, `text`, `status`, `error` | файл хранится вне Git; текст до 500 000 символов |
| `interview_questions` | Банк вопросов | `fingerprint`, `text`, `topic`, `difficulty`, `level`, `status`, `occurrences`, `lesson_id` | fingerprint уникален; урок и источник мягкие (`SET NULL`) |
| `mock_interviews` | Пробные собеседования | `user_id`, `status`, `score`, `total` | каскад с пользователем |
| `mock_interview_answers` | Ответы и разбор | `interview_id`, `question_id`, `position`, `answer`, `feedback`, `score` | каскад с собеседованием, вопрос мягкий |

`lesson_progress` — осознанное исключение из общих правил: у неё нет своего `id`
и пары `created_at`/`updated_at`, потому что строка означает только сам факт
завершения урока. Составной первичный ключ не даёт сохранить две отметки одной
пары, а запись выполняется через `INSERT ... ON CONFLICT DO NOTHING`: два
одновременных запроса не создают дубль и не падают с ошибкой.

Общее для всех таблиц:

- `id` — `BIGSERIAL`, первичный ключ. У таблиц-связок и отметок его может не быть:
  там используется составной ключ (`lesson_progress`, `quiz_attempt_selected_options`).
- `created_at`, `updated_at` — `TIMESTAMPTZ`, заполняются базой (`DEFAULT now()`);
  `updated_at` обновляется при изменении строки через ORM. У неизменяемых записей
  есть только `created_at` (попытки квизов, выделения), у отметки прогресса —
  `completed_at`.
- `position` — порядковый номер внутри родителя, начинается с 1. Уникальность пары
  «родитель + номер» не даёт двум урокам занять одно место и заодно служит индексом
  для выборки «все уроки модуля по порядку».
- Имена ограничений строятся по единому правилу (`pk_`, `fk_`, `uq_`, `ck_`, `ix_`),
  заданному в `app/db/base.py`, — например `uq_lessons_module_id_position`.

Типы блоков урока: `heading`, `text`, `code`, `callout`, `image`, `table`, `list`.
Содержимое блока лежит в JSON, потому что у разных типов оно устроено по-разному.

### Начальные данные (сид)

`app/db/curriculum_data.py` содержит структуру основного курса — 9 модулей и 70 уроков
из CURRICULUM.md. `app/db/seed.py` переносит её в базу. Сид идемпотентный: создаёт только
недостающие строки и не меняет существующие.

`app/db/demo_lesson.py` публикует курс и первый урок, наполняя его 14 блоками
по методике. Это единственный опубликованный урок этапа 4: тексты остальных уроков
и квизы создаются на этапе 9. Остальные 59 уроков остаются черновиками и не попадают
в ответ API. Повторный запуск сида не перезаписывает блоки и не публикует заново урок,
который сняли с публикации: контент меняется через административную панель (этап 7).

## 6. Как части общаются: пример

Индикатор «Сервер работает» в футере сайта:

1. Браузер загружает страницу с frontend (`localhost:3000`).
2. Компонент `BackendStatus` вызывает `fetchHealth()` из `lib/api.ts`.
3. Уходит запрос `GET http://localhost:8001/api/v1/health`.
4. Backend проверяет базу запросом `SELECT 1` и отвечает JSON.
5. Компонент показывает результат.

Backend разрешает запросы с адреса frontend через CORS (`CORS_ORIGINS` в `.env`).

## 8. Учебный стенд

`training_stand/` — отдельное приложение для практики недель 5–8 и итогового
проекта. Оно не связано с основной базой и backend LoadLab: свой контейнер,
том SQLite и порт 8082.

- FastAPI + SQLite; простой HTML-интерфейс и JSON API.
- Вход по почте и паролю выдаёт токен; API принимает `Authorization: Bearer`.
- Товары, поиск, корзина, заказ, история заказов; тестовые пользователи и товары.
- `POST /api/admin/reset` с заголовком `X-Reset-Token` возвращает стенд
  в исходное состояние.

Подробности для ученика — `training_stand/README.md`.

## 9. Известные ограничения текущего этапа

- Нет восстановления пароля, подтверждения email, входа через сторонние сервисы и 2FA.
- Ограничение попыток входа хранится в памяти одного процесса backend.
- IP-адрес клиента берётся из соединения; за обратным прокси потребуется учитывать
  заголовок `X-Forwarded-For`.
- Нет автоматических тестов интерфейса — только линтер, проверка типов и ручная проверка.
- Опубликован только один демонстрационный урок: каталог и прогресс работают,
  но полноценная программа наполняется на этапе 9.
- Квиз реализован для урока; итоговые квизы модулей и разминки поддержаны моделью,
  но их API и контент появятся на этапе 9.
- У таблицы `sessions` индексы по `user_id` и `expires_at` появились вместе
  с этапом 4. Ограничение попыток входа по-прежнему хранится в памяти процесса.
- Если backend недоступен, интерфейс считает посетителя гостем: в шапке появляется
  «Войти», а `/profile` отправляет на страницу входа. Данные при этом не теряются:
  права всё равно проверяет сервер.
- В контейнере backend читает `.env` только через переменные, которые передаёт
  `docker compose` (`ENVIRONMENT`, `CORS_ORIGINS`, `POSTGRES_*`). Новая настройка,
  добавленная в `.env`, попадёт в контейнер лишь после того, как её добавят
  в `infrastructure/docker-compose.yml`.
- Конфигурация рассчитана на локальную разработку, не на публикацию в интернете.
